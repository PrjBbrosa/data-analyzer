真正的优势（不只是"风格一致"）

  1. Mode 段 = Validation Ladder L 层入口。 顶栏 资产/Preflight/Manifest/Replay/Capture 和 roadmap §2 的 L1–L4 一一对应；操作员看 docs/analyzer/acquisition/...validation-roadmap.md 时心里有什么名词，Cockpit 里就能找到对应的 tab。这是其它三个方案做不到的"语义同构"。
  2. 左栏的会话浏览解锁了 roadmap §3 数据资产库。 "按车型/平台/ECU 软件版本/场景/issue_tag 检索 MF4"这件事，需要持久树 + chip 过滤 + 表格的组合；wizard 或 tab 都装不下。这块是当前 acquisition 最缺、价值最大的能力。
  3. StatusBar 给长任务一个家。 对 30 个 MF4 跑一次 preflight.sha256_file() + analyze_mf4() 是分钟级的事；Analyzer 的 StatusBar 已经被 FFT-vs-Time 进度占着，再塞 acquisition 会撞车。独立窗等于多了一条进度通道。
  4. "在 Analyzer 打开"是真二端口工作流。 Cockpit 选中可疑文件 → 点按钮 → Analyzer 同桌面接收并加载。两个窗各做各的，不抢主线程；这是单窗口方案给不了的体验。
  5. Capture 槽位预留，Windows + Vector 上线零重构。 顶栏 Capture 现在 disabled，等 can_logger/p0/vector_probe.py 在 Windows 上落地时只需注册一个新的 stack page，不动其它 mode。
  6. 对长 inspector_sections.py（3033 行）友好。 Cockpit 的 Inspector 只装资产/SHA/preflight 字段，跟分析侧完全解耦——不会让那个本来就大的文件再大。

真正的代价（不是"重复造轮子"那种空话）

  1. 必须先做一次"UI 公共件抽取"重构。 ui/icons.py、_palette.py、_fonts.py、drawers/、widgets/searchable_combo.py 这一批要从 mf4_analyzer/ui/ 提到 mf4_analyzer/ui_kit/，否则 Cockpit 反向依赖 Analyzer UI 模块会破坏层级。这是 1–2 天的纯重构，对 analyzer 用户来说"看不到差别但合并时容易冲突"。
  2. 需要两个 setStyleSheet 入口点。 app.py 的 _load_stylesheet 现在只跑一次；Cockpit 需要复用同一段加载逻辑（外提为 ui_kit.stylesheet.load(app)）。每次改 QSS，要在两个进程都验过。轻微但持续的维护税。
  3. "两个窗"对用户认知有成本。 "我要去哪个窗？"在初期会问 5 遍。需要在 Analyzer 的 File 菜单里加一个 打开 Acquisition Cockpit…，并在 Cockpit 状态栏写清楚"分析请在 Analyzer 里做"。这是产品层面要写清楚的小事。
  4. 数据资产库的 in-repo / NAS 双源要写得很小心。 Left tree 上的 extended (NAS) 节点必须在离线/未挂载时表现得体面：明确灰显、点击不阻塞 UI、给"为什么不可见"的提示。这是 happy path 之外要真正测的边界。
  5. 窗口名 / 安装包 / 桌面图标 / 命令行入口（python -m mf4_analyzer.acquisition）都要定一遍。 别小看：PyInstaller 打包脚本 .build-tools/ 要新增一条 spec，CI smoke 要多跑一个目标。
选 A 当：

验证程序是未来一个季度的中心；asset library 文件数 > 30；至少 2 人会同时用；目标是"上车调试 → 上车确认"这条线真正立起来。

别选 A 当：

验证只是顺手做做、文件量小于 20、且只有 1 人在用——大杀器的维护成本会反过来咬人。

实际工作量：

2–3 周。Week 1: ui_kit 抽取 + Cockpit 骨架 + 资产 mode 表格。Week 2: Preflight / Manifest mode。Week 3: Replay + 测试 + 打包。

真正的优势

  1. 顶栏 mode_changed 信号现成。 ui/toolbar.py 已经有 'time' | 'fft' | 'fft_time' | 'order' 的 ButtonGroup；加一个 'acquisition' key + 一个 stack page，set_enabled_for_mode 加一行——这是从设计上就允许的扩展点。
  2. "分析中发现可疑文件 → 切去采集做 Preflight → 切回继续"是一键的。 文件、Inspector 状态都不丢，操作员的工作流是连续的。这是 A 方案的两个窗做不到的（A 是把它换成"在 Analyzer 打开"按钮，多走一步）。
  3. 不需要重构 ui_kit。 直接 from .icons import Icons、from .drawers import ... 复用就行；最小动作面。一周可见上线。
  4. 对小团队 / 验证程序刚起步时正合适。 你不知道 acquisition UI 最终长什么样的时候，先塞进 Analyzer 用一段时间，等需求长清楚再决定要不要切成 A。这是"廉价试错"。
  5. QSS 改一次两边都生效。 Precision Light 调色微调，acquisition 同步获益，零额外维护。

真正的代价

  1. "mode" 这个抽象本来是"同一文件的不同呈现"，被强行扩成了"完全不同的动词"。 时域/FFT/阶次都是 view；采集是 configure-and-run。共用 mode segment 会让"切换到采集就把图表清空"这件事看起来像 bug。
  2. FileNavigator 必须双语义。 分析模式下它是"文件 + 通道树"；采集模式下它是"Session 浏览"。两个语义共用一个 widget 会导致 file_navigator.py（现在 255 行）变成带 mode-aware 状态的复杂控件——非常容易出"切换后 selection 串台"的回归。这是这条路最大的暗坑。
  3. Inspector 矩阵爆炸。 inspector_sections.py 现在 3033 行，已经被同事 flagged 太大。每个 section 都要加 enabled_for_modes={'time','fft','acquisition'} 这种过滤，组合数随 mode 数线性涨。
  4. 单窗口竞争主线程。 分析侧已经有 FFTTimeWorker 在 worker QThread 跑长任务；acquisition 的 SHA-256 / preflight sweep 也是长任务。它们要么共享 Worker 队列（要写调度），要么各自起 thread（StatusBar 进度信息冲突）。两条路都不省事。
  5. "采集"塞进去之后，去掉就很难。 一旦操作员习惯了"在 Analyzer 里也能跑 preflight"，再想切到 A 方案就要做产品迁移说明、文档更新、对外培训——这是认知锁定。
  6. 未来的 Capture（Vector live）几乎一定塞不进去。 live 采集需要常驻、长时间运行、不能被分析操作打断。把它和分析共一个 MainWindow 是反直觉的；这一步实质上把 Capture 排除在外了。
选 B 当：

需要 1 周内出可用版本；acquisition 短期就只做 Preflight + Manifest 两件事；团队就 2 人；做完一阵子再决定要不要走 A。

别选 B 当：

明知道未来要做 live Capture / 资产库浏览 / 多人共用——把 acquisition 提前耦合进 Analyzer，等到要拆的时候每一行都要回滚。

实际工作量：

4–6 天。Toolbar 加 mode + ChartStack 加 page + FileNavigator 加双语义 + Inspector 加 sections + smoke 测试。

真正的优势

  1. 1:1 对应 roadmap §2 验证阶梯。 第 1 步配置 / 第 2 步选源 / 第 3 步 Preflight / 第 4 步 Manifest / 第 5 步回归——操作员看 roadmap 文档时记的步骤，在 Wizard 里就是这个顺序。教学成本几乎为零。
  2. 步骤是强制 gate。 Preflight 没过不让进 Manifest，回归没过不让进完成。这正是 roadmap 说"把上车调试降级为上车确认"想要的纪律。同样的纪律放在 A/B 的自由编辑面板里就靠不住。
  3. 每页是独立 QWidget，单测最容易。 不需要起 QMainWindow，pytest-qt 直接 instantiate 每一页，validatePage() 是纯函数式的"输入 → 是否能继续"。CI 友好度最高的方案。
  4. 对 Analyzer 0 耦合。 Wizard 是 modal 工具，跟 mf4_analyzer/ui/ 没有任何 import 关系——Analyzer 升级 / 重构都不会牵连它，反之亦然。
  5. Wizard 页面的状态机可以无 GUI 复用为脚本。 把每页的 validatePage 提到 acquisition/runners/，CLI 模式可以跑同一套逻辑——例如 CI 上自动批处理整个 data/golden/。这是 A/B 拿不到的副产品。

真正的代价

  1. "浏览资产库"是 Wizard 的反模式。 roadmap §3 的核心能力是"按车型 / 平台 / ECU 软件版本 / 场景 / issue_tag 检索 MF4"——这是 needs-driven，不是 task-driven。Wizard 本质上只能"开一个新任务"，回头看以前的 manifest 必须额外做一个"manifest 浏览器"页面，那其实又退化成了 A。
  2. 状态不持久。 操作员关了 Wizard，下次再开还要重选 DBC / A2L / alias 文件。可以做 last-used 默认值，但仍然是健忘的——不像 A/B 那样有一个常驻的"工作空间"。
  3. Modal 阻断分析交叉验证。 在 Manifest 步骤想"先回 Analyzer 看一眼这个 MF4 的某个信号长啥样再决定打不打 issue tag" —— 要么关 Wizard 丢状态，要么 Analyzer 没有上下文。Cross-reference 工作流被破坏。
  4. 批量场景困难。 对 data/golden/ 的 30 个文件做一次性 preflight + manifest 更新，用 Wizard 是 30 × 5 步 = 150 次点击。最后一定会被偷偷加一个"高级模式"或"批处理"按钮，那其实就是 A 方案的简陋版。
  5. "manifest 一旦写了又改"是常态。 issue_tags 不是一次写定的——三天后看到新现象，要回去补 tag。Wizard 是"创建"型而非"维护"型 UI，长期会成为障碍。
  6. Vector live capture 几乎不能塞进 Wizard。 live 需要常驻 + 长时间 + 中途可暂停；Wizard 强制线性走步骤，模型对不上。最终 Capture 会另起一个面板/窗，那就是 A + C 两套并存。
选 C 当：

验证流程是 SOP 化的；每次只处理 1–2 个新文件；操作员是测试工程师而不是研发；想立刻有"教学价值高、不会出错"的工具。

别选 C 当：

需要 manifest 浏览 / 资产库 / live capture 中任何一个——Wizard 装不下，最后会和其它方案并存。

实际工作量：

3–5 天。6 个 QWizardPage + state machine + YAML 渲染 + pytest-qt 单测。最便宜也最局促。

方案 D

Bench Console — 台架前的单页操作面板

为 L4 台架而生 · 当下用不上 · 解决不了离线问题

不是 Analyzer 风格——单页、深色、大字号，给台架旁站着的工程师看。LCD 风格数值瓦片 + rolling time strip + 大按钮 [Arm / Capture / Stop]。Inspector 折到右边抽屉。需要 Windows + Vector 才有用。

真正的优势

  1. 为台架而生，不假装做别的事。 Operator 站在 2 米外读得清楚 — 28 px 大字号、深色背景、心电监护器风格。Analyzer 的 12 px Precision Light 在台架现场是看不清的。
  2. 注意力路径最短。 Arm → Capture → Stop 三个红 / 黄 / 绿大按钮，配合 bus load / dropped frames 警示，决策点压缩到 2 秒内。
  3. 硬件作用域窄到极致。 只对接 can_logger/p0/vector_probe.py + 一个 live MF4 writer。不碰 manifest、不碰 preflight、不碰资产库 — 边界清晰、bug 面积小。
  4. "第二屏"型副工具。 Engineer 主屏跑 Analyzer 或终端，副屏挂 Bench Console。这是 A/B/C 都不擅长的角色。
  5. 对 PyQtGraph / blit 优化友好。 单页 + 单 strip 的架构很容易把渲染抠到 60 fps。Analyzer 那种多 chart + 多 canvas 的情况想做 live 反而麻烦。

真正的代价

  1. 它解决不了当前最痛的离线验证瓶颈。 现在 acquisition 的工作面在 L1–L3（preflight / manifest / sha / regression），全是离线、文件型、表格型的。Bench Console 是 L4 才生效的工具——而 L4 在 Vector 硬件 + Windows 就绪前是没法用的。
  2. 它和 Analyzer 视觉是分裂的。 深色 + 大字 + LCD 风格不可能套 style.qss。第二套视觉系统 = 第二套设计维护工作（icon 集、字号阶、配色）。
  3. 硬件相关的代码会进来。 python-can[vector] / pyxcp 这些 Windows-only 包目前是 platform-gated。Bench Console 让它们成为运行时强依赖；CI / 测试 / 打包都要为这个新角色单独配 Windows runner。
  4. "manifest / 资产库 / regression"在这里仍然没有 UI。 大概率最后变成 D + (A 或 B) 并存——D 单独存在意义不大。
  5. 一年 80% 时间没人用。 台架测试不是天天做。这个面板的"每次启动"成本 vs "每月使用"次数比例最差。
选 D 当：

台架测试 ≥ 每周一次；有专门的台架操作员；Vector 硬件已就位；想要"第二屏专用看板"——而且你已经有 A 或 B 在做离线验证。
