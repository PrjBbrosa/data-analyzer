二、关键问题：为什么会觉得错乱

按用户可见影响排序；这是当前主分支的代码与探针结果，不是从截图推断。

P1

模式切换没有应用目标 View

进入另一分析时只切页面和 Inspector 卡片，没有调用目标分析 View 的完整 apply；回到时域也只按当前左侧勾选重画，没有恢复时域 View 保存的通道。

结果：FFT 新建空 View 清空左侧后，回到时域仍是空白，即使时域 View 状态里还保存着原通道。
P1

新建 View 的继承规则不一致

所有分析新 View 的模型都是空 Pane + 空 params，但空 params 的 apply 是 no-op。于是参数控件保留上一 View；时频/阶次的来源也保留，FRF 却会清空来源。

结果：“+”既不像新建空白，也不像复制当前；用户无法预判。
P1

共享时间范围会跨模式反写

范围复选框按模式保存，但起止数值只有一份。FFT 保存 0.4–0.5，时域改成 0.1–0.2，再回 FFT 后，0.1–0.2 会覆盖 FFT View 的原范围。

结果：这不是单纯显示残留，而是当前 View 的持久状态被错误改写。
P1

左侧通道树有两个主人

文件范围来自当前焦点时域 View；FFT 又直接用左侧勾选作为分析来源；时频、阶次和 FRF 则在右侧 Inspector 选择来源，左侧勾选与结果无关。

结果：同一处勾选在不同模式下含义变化，但界面没有说明。
P2

“显示”列的代码与回归合同冲突

当前代码在分析模式只移除通道眼睛图标，保留该列给文件移出动作；现有测试仍要求整列隐藏，实跑为失败。

结果：列标题仍叫“显示”，但内容已经变成另一种操作，语义不清。
P2

状态模型正确，控件投影不对称

AnalysisViewState 已经把 View 级参数和 Pane 级来源分开，切换 View 也有 capture → apply → cache-render 管线；缺口集中在模式入口与空状态初始化。

结果：无需推翻多 View 架构，优先修正少数入口即可显著改善。

四、对四个问题的直接回答

每一项都分“现在是什么”和“理论上应该是什么”。

01

选好分析后，下方新增 View 是什么样？

当前

模型是空 View，但 Inspector 可能继续显示上一 View 的参数；时频/阶次还保留上一来源，FRF 清空来源，FFT 清空左侧勾选。行为不统一。

应当

“+”固定创建空白 View：只继承可用文件范围，来源为空、参数为该分析默认值、范围为空、无结果；“复制 View”才完整复制来源、参数、范围与分屏。

02

切换分析后，左侧通道文件应该是什么样？

当前

顶部文件区保持全局打开文件；下方通道树仍投影焦点时域 View 的文件。FFT 使用勾选；其他分析只把这些通道当右侧下拉候选，左侧勾选可能与结果无关。

应当

文件区保持全局；通道区明确标注“来源范围：时域 View X”。切换分析后，选中态必须投影当前分析 View / Pane；如果该模式只能在右侧选来源，左侧应改为只读候选并给出说明，不能保留误导性勾选。

03

实际操作应该遵从什么顺序？

当前安全顺序

打开文件 → 确认文件已加入目标时域 View → 进入目标分析 → 先选/新建分析 View → 按模式选择来源 → 设范围与参数 → 计算。用“+”后必须重新核对来源与范围；需要继承时优先“复制”。

推荐产品顺序

打开数据 → 选择分析类型 → 选择 View → 选择焦点 Pane → 选择来源角色 → 设置参数 → 计算。界面应按这条顺序从左到右自然引导，不要求用户记住 FFT 与其他模式的例外。

04

右侧 Inspector 是否应该继承？什么时候继承？

当前

View 切换时会应用保存的 params；但新 View params 为空时不重置，模式切换又没有完整应用目标 View，因此出现隐式继承和跨模式范围串扰。

应当

Inspector 只继承“明确属于当前对象”的状态：切换已有 View 时恢复该 View；切换 Pane 时恢复 Pane 局部字段；复制 View 时复制全部。新建空白和跨分析切换都不从上一上下文隐式继承。

六、建议采用的继承边界

“继承”必须由明确动作触发；普通切换只做恢复，不做复制。

M切换分析类型

恢复目标类型当前 active View，不读取上一类型的 Inspector 数值。

  • 来源：恢复目标 View / Pane
  • 参数：恢复目标 View
  • 结果：仅从缓存显示，不自动计算

V切换已有 View

完整投影该 View；Inspector 不保留 outgoing View 的草稿。

  • View 级：计算参数、显示参数、分屏选项
  • Pane 级：来源、范围、游标、轴范围

＋新建空白 View

只继承“可用文件范围”这一环境，不继承分析意图。

  • 来源为空
  • 参数为该分析显式默认值
  • 无范围、无结果、单 Pane

⧉复制当前 View

这是唯一默认复制全部工作意图的动作。

  • 复制来源、参数、范围、分屏
  • 生成新 view_id
  • 允许命中相同缓存，但不自动重算

P切换焦点 Pane

Inspector 只切换 Pane 局部字段，View 级参数保持不变。

  • 局部：来源、时间范围、游标、有效结果事实
  • 共享：窗函数、NFFT、显示策略等 View params

SPreset / 模板

跨 View 复用参数应通过显式 preset，而不是靠控件残留。

  • 应用后写入当前 View
  • 清楚显示覆盖范围
  • 不偷偷改其他 View / Pane

七、怎么改更合理

先统一行为，再做视觉增强；不需要先重构全部 MainWindow。

P0 · STATE CORRECTNESS

统一模式入口投影

  • 离开时 capture outgoing context。
  • 进入时 apply target active View；回时域必须恢复 Time View。
  • channels_changed 只写当前真正 owner，禁止分析模式误写时域 View。
  • 共享范围的勾选与数值都按 View / Pane 保存和恢复。
P1 · PREDICTABLE CREATION

让“+”和“复制”语义互斥

  • 新建时创建完整默认 params，不再用空 dict + no-op。
  • 所有分析新 View 都清空来源，保持一致。
  • 复制保留来源、参数、范围、分屏，并显示“复制当前 View”。
  • 无来源画布显示下一步提示，而不是只显示空白。
P2 · LEFT RAIL CLARITY

明确左侧到底在控制谁

  • 通道区顶部显示“来源范围：时域 View 1”。
  • FFT 显示多选来源；时频/阶次/FRF 改成只读候选或角色标记。
  • 分析模式不要保留无意义勾选高亮。
  • “显示”列与“移出 View”拆分或改成准确标题，并同步测试。

十、后续实现的验收线

如果按本报告优化，至少需要以下状态迁移用例；前台 TraceLab 仍是独立视觉门槛。

Time A → FFT B → Time

回到时域必须恢复 A；FFT 的 B 只属于 FFT View。

五种模式的新建空白

来源、参数、范围和空态提示必须按统一合同落地。

复制 View

来源、参数、范围、分屏相同，view_id 不同，不自动计算。

跨模式范围隔离

每个 active View / Pane 的起止值、勾选状态互不覆盖。

Pane 焦点

只回填 Pane 局部来源/范围/事实，不能改写 sibling。

左侧语义

每种模式的勾选、角色和操作列标题与实际动作一致。

项目保存 / 恢复

inactive section 以 PaneState 为事实，不读取当前 navigator 覆盖。

前台验证

真实 macOS TraceLab 中检查切换、空态、焦点和 Inspector 回填。

最终建议：不要让用户学习“FFT 看左边、时频看右边、FRF 又会清空”的隐藏规则。产品应保证任何时刻只有一个清楚的 active context，并让左侧、画布、底部 View、右侧 Inspector 同时指向它。
