# P0 — XCP Acquisition Feasibility Spec Note

**Date:** 2026-05-14
**Module:** P0 — XCP / Vector hardware feasibility (independent track)
**Plan (source of truth for steps):** [`../plans/2026-05-13-xcp-acquisition-p0.md`](../plans/2026-05-13-xcp-acquisition-p0.md)
**Program index:** [`../plans/2026-05-14-data-acquisition-validation-program.md`](../plans/2026-05-14-data-acquisition-validation-program.md)

This spec note describes intent, gates, and the **environment caveat** for executing P0 on the current host. The plan remains the source of truth for the seven tasks and their commands.

## Intent

Prove the analyzer can:

1. Write an MF4 with one signal and load it back through the existing `mf4_analyzer.io.loader.DataLoader.load_mf4` (hardware-free).
2. Parse a real A2L file's measurement summary via `pya2ldb` (host-only; environment-gated by `P0_A2L_PATH`).
3. Open a Vector CAN channel on Windows via `python-can[vector]`.
4. Exchange XCP CONNECT and SHORT_UPLOAD frames with a powered ECU and decode one value.
5. Persist that one value as an MF4 that round-trips through the existing loader.
6. File the evidence — commands, raw output, blockers, verdict — in `docs/analyzer/acquisition/P0_Runbook.md`.

P0 runs on its own branch (`feat/xcp-acquisition-p0`) and is independent of Modules A/B/C. Its verdict (`PASS` or a narrow documented `PARTIAL`) is what unblocks production DAQ work.

## Acceptance gates

Per the program index, P0 reaches its module-level gate when `P0_Runbook.md` records a verdict in `{PASS, PARTIAL}` with a documented next action. The plan §"P0 Completion Gate" expands this:

- MF4 compatibility test passes (Task 2 — hardware-free; executable here).
- Real A2L parse either passes or has a documented parser blocker (Task 3 — environment-gated; executable here if `P0_A2L_PATH` is provided).
- Windows Vector open either passes or has a documented driver/config blocker (Task 4 — **hardware-blocked on macOS**).
- XCP `CONNECT` and `SHORT_UPLOAD` either pass or have a documented ECU/protocol blocker (Task 5 — **hardware-blocked on macOS**).
- `P0_Runbook.md` contains the actual command/output evidence per §Task 7.

## Execution environment

**Host:** macOS (Darwin 25.5.0). This caveat is the load-bearing reason this spec note exists.

Per-task executability on the current host:

| Plan task | Description | Status on this host (macOS) |
| --- | --- | --- |
| Task 1 | Create clean branch + verify venv imports (`asammdf`, `can`, `pyxcp`, `elftools`, `pya2l`) | Executable here |
| Task 2 | Prove MF4 output loads through existing analyzer (hardware-free) | Executable here |
| Task 3 | Parse A2L measurement summary; pytest is `@skipif` gated on `P0_A2L_PATH` | Executable here (test SKIPS without `P0_A2L_PATH`; runs against real A2L when provided) |
| Task 4 | Verify Vector hardware access on Windows | **HARDWARE-BLOCKED on macOS** — `vector_probe.py` exits 2 with the message "Vector interface is expected to run on Windows" |
| Task 5 | Verify XCP CONNECT and SHORT_UPLOAD against powered ECU | **HARDWARE-BLOCKED on macOS** — requires Vector CAN driver + powered ECU on Windows |
| Task 6 | Capture one read value as MF4 (extends the XCP probe with `--mf4-out`) | **HARDWARE-BLOCKED on macOS** — depends on Task 5 having a live bus and ECU |
| Task 7 | Write P0 runbook results and verdict | Executable here for the structure; the Vector/XCP fenced blocks stay marked BLOCKED until a Windows + Vector + ECU session runs |

When Tasks 4, 5, and 6 run on macOS, they are recorded in `P0_Runbook.md` using the §Task 7 verdict template (Verdict ∈ `{PASS, PARTIAL, BLOCKED, FAIL}`) with **Verdict: BLOCKED**. Verbatim rationale to paste under the Reasons list:

```text
Verdict: BLOCKED

Reasons:
- Current host is macOS; python-can Vector interface requires Windows + Vector CANalyzer/CANoe driver.
- vector_probe.py exits 2 on this platform by design (sys.platform != "win32") and prints "Vector interface is expected to run on Windows".
- XCP CONNECT / SHORT_UPLOAD (Task 5) and the MF4 capture extension (Task 6) cannot be exercised until a Windows host with the Vector driver and a powered ECU is available.
- Re-run Tasks 4, 5, 6 on the Windows worktree and replace these BLOCKED blocks with PASS or FAIL outputs.
```

The block above is the runbook entry; it is copied here so this spec, the runbook, and the plan remain reconcilable.

## Out of scope

- Production DAQ streaming, DAQ UI tab, realtime plotting of live acquisition values — all deferred per program index until P0 verdict is PASS or a documented narrow PARTIAL.
- Adding `python-can[vector]`, `pyxcp`, `pya2ldb`, or `pyelftools` to `requirements.txt` — deferred per program index "Deferred Until P0 PASS".
- Seed/key handshake for ECUs that gate SHORT_UPLOAD on it — explicitly called out as a known PARTIAL trigger in the program index; if encountered, P0 is recorded as PARTIAL pending a follow-up that adds seed/key.
- Any change to `mf4_analyzer/io/loader.py` — the loader contract is what P0 round-trips through, not what it modifies.
- Mixing P0 commits onto the Module A/B/C feature branches — P0 has its own branch.
